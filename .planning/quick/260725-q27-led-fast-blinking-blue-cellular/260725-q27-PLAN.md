# Quick task q27 — Fast blinking blue = cannot join the cellular network

**Date:** 2026-07-25
**Spec:** DOC-14
**exit-impact:** ops

## Problem

Support sees traps whose LED blinks blue quickly. That is the cellular stack
retrying a network join it never completes, so the trap never reaches the
cloud and shows offline in the app. The guide had no entry for it. Blue was
documented only as **solid** (unarmed, door open) and **blinking after a
command** (opening the door), so a customer reading the LED Guide either found
nothing or landed on the wrong meaning.

## Plan

1. Add a `blue` / `fast-blink` entry to the `led-diagnostics` block in
   `getting-started/led-guide.md`. That block is the single source for both
   the interactive wizard and the reference table on the page, so one entry
   covers both surfaces. Use `context: idle, not after a command` to keep it
   distinct from the door-opening blink.
2. Add a row to the Step 3 LED table in
   `troubleshooting/trap-offline-or-wont-connect.md`, and a warning hint in
   Step 4 so the coverage section says plainly that a persistent fast blue
   blink is a support call, not a field fix.
3. Add a row to the System Status LEDs table in
   `OcuTrap_Knowledge_Base_Complete.md` (hand-maintained, feeds the KB PDF).
4. Mirror root ↔ `docs-site/content/` byte-identical for all three pages.

## Out of scope

- Root-causing why the join fails (SIM, coverage, antenna, modem). The
  customer-facing instruction is coverage check then support.
- Firmware LED changes. This pattern comes from the Particle system LED while
  application RGB control is released; `LEDManager` never drives blue for
  connectivity.
- KB PDF regeneration — CI rebuilds on merge to `main`.
